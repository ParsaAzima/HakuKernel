Building the Haku kernel

One script builds the image, boots QEMU and checks the log.

build.py owns every step: NASM, clang-cl, lld-link, the FAT12 and cpio packers, and the QEMU runs. CMake is only a test front end — it registers the four headless gates under stable names so CI and a workstation run the same commands.

01

Host requirements

Host tools
ToolVersionNotes
LLVM19+clang-cl and lld-link; no Visual Studio install and no MSVC headers are needed. CI builds with the distro package.
NASM2.16+The boot sector, entry paths and ISR stubs. The local build uses 3.02; CI uses the distro package.
QEMU8+Both qemu-system-x86_64 and qemu-system-i386.
Python3.13+Runs build.py and the image helpers in tools/.
CMake3.20+Optional. Only for ctest; build.py works alone.

Toolchain discovery. On Windows the script looks in C:\Program Files\LLVM\bin first and falls back to PATH. The switches it passes (/c, /Fo, /ENTRY, /ALIGN, /NODEFAULTLIB) are the MSVC-compatible ones clang-cl accepts; only the --target triple changes between ports.

02

Build targets and options

From the repository root
CommandDoes
python build.pyBuilds haku64.img, the x86-64 boot image. This is the default target.
python build.py runBuilds and boots it in a QEMU window.
python build.py headlessBuilds, boots headless, captures the serial log and validates every marker. Prints X64 CHECK PASSED.
python build.py headless --arch=i386The same for the 32-bit port. Prints HEADLESS CHECK PASSED.
python build.py shellBoots the 32-bit image with a static busybox as PID 1 and lands in ash, with job control and pipelines.
python build.py shell --checkScripted shell run; prints SHELL CHECK PASSED.
python build.py probe --init=FILEBoots an external static ELF32 as /init on the 32-bit image. Manual use only; it is not a CI gate.
python build.py inspect ...Lists, checks or extracts a FAT12 image without modifying it.
--smp=NGuest CPUs. 1–8 on x86-64, 1–4 on i386; the default is 2.
--memory=NGuest RAM in MiB. The default is 512; the 32-bit direct map stops at about 1000 MiB.

The headless mode exits nonzero on a missing marker, an unexpected *-FAIL line or a kernel panic. It never reports success from a timeout.

03

The four QEMU test gates

Every push builds and boots four guests. Each one asserts a marker set, so a regression in paging, the disk, the scheduler or ring-3 has to show up as a failed run rather than a log nobody reads. 

cmake -S . -B build/ctest -G Ninja
ctest --test-dir build/ctest --output-on-failure
Registered tests
CTest nameGuestSuccess line
x64x86-64, 2 CPUsX64 CHECK PASSED
x64-smp4x86-64, 4 CPUsX64 CHECK PASSED
i386i386, 2 CPUsHEADLESS CHECK PASSED
i386-smp4i386, 4 CPUsHEADLESS CHECK PASSED

The --smp=4 legs matter: the default two-CPU run confirms that one application processor comes online and dispatches a task, while the four-CPU run makes three of them pull work from the shared table and checks the TLB shootdown counter. A uniprocessor machine fails the SMP-AP-OK assertion instead of passing quietly.

The tests are RUN_SERIAL because each one builds an image, binds a QEMU monitor port and writes its own serial log. CMake's timeout is a backstop for a wedged emulator; the waits inside build.py are shorter and name the marker that never arrived.

04

Boot and data images

What the build produces
PathRole
haku64.imgPrimary bootable floppy image for x86-64.
build/haku64_fs.img1.44 MB FAT12 ATA disk seeded with the test files, INIT.ELF and X64MOD.HKM. Rebuilt on every run.
haku.imgBootable floppy image for the 32-bit port.
build/haku_fs.img32-bit data disk with the user ELFs and initramfs. Treated as user data.

On the 32-bit data disk. build/haku_fs.img is reused untouched unless you pass --fresh. python build.py inspect --check verifies its BPB, FAT mirrors and cluster chains without writing to it. If it is damaged, report it instead of deleting it out of hand.

05

CI and release pipeline

GitHub Actions runs the gates on ubuntu-latest: one matrix leg for x86-64 and one for i386, each installing NASM, LLVM, QEMU, CMake and Ninja from apt, configuring the CTest suite with the Ninja generator, and running ctest -R "^x64" or -R "^i386" so both the default and the four-CPU test run. The serial logs, screen captures, register dumps and both boot images are uploaded as artifacts for fourteen days.

A tag builds the release: both ports boot headless, the data images are rebuilt from scratch, and haku64.img, build/haku64_fs.img, haku.img, build/haku_fs.img, the README and the licence are zipped with a SHA256SUMS.txt.

06

Troubleshooting the build

The troubleshooting document covers the failures that actually come up: a missing clang-cl on PATH, NASM section and symbol mismatches against LLVM COFF objects, an x86-64 image that will not fit the loader's window, QEMU monitor ports still held by an earlier run, and a 32-bit data disk the kernel refuses to mount.
