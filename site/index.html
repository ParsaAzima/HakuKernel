Freestanding x86 kernel · GPL-3.0

A small operating system that boots from a floppy and runs code at ring 3.

Haku is an operating system written in C and NASM. A two-stage BIOS loader enters long mode; the kernel builds its own page tables, heap, scheduler, filesystems and module loader; static ELF programs run unprivileged against a Linux-inspired syscall ABI. No C runtime underneath, no hosted library inside, no hardware virtualization.

01

A freestanding x86-64 kernel

Haku is a teaching-sized kernel with production habits. It boots on a BIOS machine from a 1.44 MB image, takes the memory map from E820, builds page tables and a direct map over physical memory, installs its own descriptor tables and interrupt gates, then hands the machine to a 100 Hz preemptive scheduler. From there it loads a static ELF image into a per-process address space and drops to privilege level 3.

The kernel never links a hosted library. LLVM's clang-cl compiles the same C sources for the i686 and x86-64 System V targets, NASM assembles the entry paths, and lld-link produces a fixed-base image that tools/pe2bin.py flattens for the loader. The build and the QEMU test runs are driven by one Python script.

  • Two-stage boot loader: A20, GDT, protected mode, E820, then PAE and long mode on x86-64.
  • Frame allocator, kernel heap, copy-on-write fork, execve, wait4 with WUNTRACED/WCONTINUED, process groups and sessions.
  • clone threads with futex, a pthread subset, robust mutexes and condition variables, per-thread errno.
  • ATA PIO, a writable FAT12 driver behind a VFS, ramfs, devfs, procfs and a cpio initramfs.
  • A ring-3 ELF loader with validated user pointers, -errno results and NX enforcement.
  • Loadable .hkm modules with an export table and a strict unload protocol.
02

Boot chain and memory management

The x86-64 port reads the E820 map, maps physical memory with 2 MiB pages, sizes its frame pool from what the firmware reports, and installs a four-level address space with a supervisor direct map. The i386 port keeps its two-level tables and a direct map that stops below the local-APIC window. Both ports read the ACPI MADT, start the application processors through an INIT–SIPI trampoline, and give each CPU a private GDT and TSS over the shared IDT.

03

Processes, threads and scheduling

Every process owns an address space built from validated ELF segments and an 8 KiB kernel stack. fork copies pages on write, execve streams an image of up to 1.5 MiB off the disk, replaces the image and rebuilds the initial stack with argc, argv and envp, and wait4 reaps the exit status. Process groups and sessions carry kill(-pgid) and the console's foreground group, which TIOCGPGRP/TIOCSPGRP report and set. SIGSTOP parks a task in its own state and SIGCONT resumes it; wait4 reports both events without reaping. The terminal raises its own signals too: a background read stops on SIGTTIN, and a session leader's exit hangs up the foreground group with SIGHUP.

Threads come from clone: the address space and descriptor table are shared, the thread id is distinct, and a detached thread's slot and pages are reclaimed as soon as it exits. On top of that sits a pthread subset — create, join, detach, exit, robust mutexes, condition variables — with per-thread errno and TLS. Both ports pass the same create-join-mutex-cond, detach and EOWNERDEAD tests.

Every CPU schedules. On x86-64 a GS-based per-CPU block, a local-APIC timer per CPU, per-CPU idle tasks, reschedule IPIs and TLB shootdown keep tasks running in parallel and prove the shootdown reaches the target. The i386 port has the same shape: the bootstrap processor keeps IRQ0 as its tick, and the APs take their own local-APIC timer.

04

Storage: ATA PIO, FAT12 and the VFS

ATA polling PIO on both legacy channels, with software-reset recovery and a sector cache in front of the disk. On top of it a writable FAT12 driver handles files, subdirectories and 8.3 names; the VFS gives each process its own descriptor table and one mount table for the whole system.

Root
An in-RAM root populated from a cpio newc initramfs embedded in the boot image.

FAT12 at /disk on both ports, behind one mount table with longest-prefix resolution.
Rootfs
Optionally the FAT12 volume itself: python build.py rootfs mounts it at /, keeps /disk on the same bytes, and runs /INIT as PID 1.
Generated
/proc/meminfo, /proc/uptime, /proc/self/cmdline; /dev/null, zero, console.
Writes
Files are written back through the page cache; file-backed mmap maps those pages directly.
Ceiling
Eight cached paths of at most 128 KiB each, 8.3 names, no timestamps and no permission bits. An execve image is streamed into one buffer, not cached, so it may reach 1.5 MiB.
05

Framebuffer console and PS/2 input

One renderer in kernel/drivers/fbcon.c draws the Terminus 8×16 font into a VBE linear framebuffer as plain full-screen text — no status bar, no window chrome, no reserved rows — and falls back to VGA text when the firmware gives no usable mode. The same output is mirrored to COM1, so a headless run reads exactly what the screen shows.

A PS/2 keyboard decoder fills an interrupt-driven queue. The i386 port adds CSI handling; the x86-64 port adds a canonical line discipline on top of the queue — Enter commits an echoed line, Backspace erases, ^D is EOF, and ^C raises SIGINT for the foreground group. A console read() parks until a line is finished, which is what HAKU64-USER-TTY-LINE-OK and HAKU64-USER-TTY-EOF-OK prove.

06

Loadable kernel modules

A module is a packed .hkm container built on the host from NASM ELF32 or COFF i386/amd64 objects. The loader validates it, relocates it against an eleven-entry export table, and runs it at ring 0. A module can register a /dev character device or a filesystem backend and mount it at its own prefix; the kernel ties both to the module slot, refuses delete_module while a descriptor is open with -EBUSY, and detaches everything before freeing the image.

C modules are first-class: include/haku/module.h declares the services, libhakumod supplies the string and 64-bit helpers the compiler emits calls to, and the packer drops whatever a module does not reach. Both loaders offer the full set, and `romfs.c` is one C source for both ports: it registers a read-only filesystem and mounts it at /rom, which the kernel and a ring-3 program then read.

08

Limits and unsupported features

Haku does not claim POSIX compatibility. The target is an honest subset, and everything outside it returns ENOSYS rather than pretending to work. The limitations below are part of the design record, not a wish list.

  • No networking, no demand paging, no swap, no load balancing, no CPU migration.
  • No SMP-tested ring-3 task: the user-space concurrency tests still run on the bootstrap processor.
  • The x86-64 side has no shell and no scrollback: the console keeps only the visible grid and the arrow keys are ignored, while ^\ and ^Z are still plain bytes. Signals 1..31 are handled, including stop/continue, a console foreground group, SIGTTIN for a background read and SIGHUP from a session leader's exit, but the console never sets TOSTOP so SIGTTOU cannot arise, and a hardware fault is not turned into a signal.
  • FAT12 only: 8.3 names, no timestamps, no permission bits, eight cached paths of 128 KiB.
  • The rootfs is a 1.44 MB FAT12 volume: one busybox binary, no symlinks and no /etc/fstab, so applets run as /bin/busybox APP.
  • A module filesystem has no page cache and cannot be mapped; mmap answers -ENODEV and execve does not search module mounts.
  • Modules are trusted ring-0 code. There is no sandbox and no signature check.
09

Frequently asked questions

What is Haku?

Haku is a small freestanding operating system for x86-64 and 32-bit x86. It has its own boot loader, kernel, scheduler, filesystems and user C library, and it boots on QEMU or a BIOS PC from a 1.44 MB floppy image.

Which architectures does Haku support?

Two. x86-64 is the primary target, with long mode, four-level paging, SYSCALL/SYSRET and per-CPU scheduling. The i386 port keeps the 32-bit protected-mode kernel and runs a static busybox ash shell as PID 1.

Is Haku POSIX compatible?

No. Haku implements a Linux-inspired subset of the POSIX interface, and everything outside that subset returns ENOSYS. It has no networking, no demand paging and no dynamic linker.

How is Haku built and tested?

clang-cl compiles the C sources, NASM assembles the boot and entry paths, and lld-link links the image. build.py drives the pipeline and QEMU; CI runs four headless boots — x86-64 and i386, each at two and four CPUs — and asserts a marker set for every subsystem.

Can Haku run Linux binaries?

Only statically linked programs that stay inside the implemented syscall subset. The 32-bit image boots a static musl busybox, either directly as PID 1 or from a Linux-style rootfs where /etc/rc and /bin/busybox are paths on the disk. The x86-64 side runs its own C library and /INIT.ELF, and execs a static musl busybox applet from the FAT12 volume to prove a real Linux userland starts there.

Build and run Haku in QEMU

You need LLVM (nineteen or newer), NASM, QEMU and Python 3 on the PATH; no Visual Studio install is required. The build retargets the same clang-cl for i686-pc-windows-msvc or x86_64-pc-windows-msvc and links with lld-link. 

:: build the x86-64 boot image
python build.py

:: build, boot headless and verify the marker set
python build.py headless

:: the 32-bit port: busybox shell, then a Linux-style rootfs
python build.py headless --arch=i386
python build.py shell
python build.py rootfs
